## 1. 공통 Feedback — 하지 말 것 / 고칠 것 (Ⅰ, p.4~15)

### 1-1. 개조식 표현 미작성 (p.4)
- PPT 는 원칙적으로 **개조식**
- 특징 : 서술어 어미 종결형, 명사형으로 끝맺음
- 효과 : 불필요한 접속사 · 미사여구 생략 → 가독성 ↑
- 지적된 예 : "~제어신호이다.", "~필요하다.", "~둡는다." (문장형 종결)
- **적용** : `~이다 / ~한다 / ~하였다` ✗ → `~임 / ~함 / ~확인 / ~전환 / ~출력` ✓

| ✗ 문장형 | ✓ 개조식 |
|---|---|
| 파란선이 Datapath 이고 검은선이 제어신호이다. | 파란선 : Datapath / 검은선 : 제어 신호 |
| btn_D 를 누르면 edit state 로 전환된다. | btn_D 입력 → edit state 전환 |
| 1 초마다 sec 가 증가하는 것을 확인하였다. | 1 s 주기 sec +1 확인 |

### 1-2. 공백의 의미 (p.5)
- 공백 → **"자료 작성 중인 상태"로 인식**될 가능성 ↑
- 슬라이드 내용과 적합한 이미지 · 내용 삽입. **단, Fully 하게 채우지 말 것**
- 해결 Case
  - Case 1) 텍스트만 있는 개요 → **순서도 or Block Diagram** 삽입해 완성 형태로
  - Case 2) 개발 환경 목록 → **적절한 이미지 삽입 or 분할 작성**으로 공백 최소화
  - Case 3) 사용 Port 목록 → **보드 이미지 삽입 or 장표(표)로 Ports 설명**

### 1-3. 슬라이드 취합 및 내용 병합 (p.6)
- 동일 제목 슬라이드 多 → 단순 내용 나열 (장황함) ↑
- **Numbering or 핵심 내용만 간략하게** 기술
- 예 : "보드 설명" 2 장 → 보드 사진 1 장에 부품별 Callout 박스로 **1 장 취합**
- 예 : 같은 모듈 시뮬 캡처 6 장 연속 → 핵심 파형만 남기고 통합

### 1-4. Text 내용 vs Image (Sch. / Timing Diagram) Mapping X (p.7)
- 순서 or 해당 Block 미표기 → 가시성 · 가독성 ↓
- 하단에 bullet 4 줄 + 위에 Schematic 그림만 있고 **어느 줄이 어느 블록인지 연결 없음** → 지적
- **Text 내용과 Matching 하여 표시 & 핵심 내용 기입** 권장
- FSM / Timing Diagram 은 **Status Matching** (텍스트의 상태명 ↔ 그림의 상태 구간) 으로 설명하는 게 효과적

### 1-5. 단순 Text 서술 지양 (p.8)
- Text 비중 ↑ → 가시성 · 가독성 저하 / Highlight 多 → 논점이 흐려짐
- Case 1) Text 보단 **장표(표)로 정리** → 가시성 · 가독성 ↑
- Case 2) **필요 부분에만 Highlight** → 개연성 · 전달력 ↑ (노란 형광펜을 문단 전체에 칠한 예가 지적됨)

### 1-6. 미괄식 자료 작성 (p.9)
- **두괄식(상단)** : 슬라이드 내용 요약 (결론) — ex) `검증 결과 : 정상 동작함`
- **미괄식(하단)** : 기타 주석 · 보강 내용, **Text 는 작게** — ex) `Note. 5800 / 58 = 100cm`
- 지적된 예 : 시뮬 슬라이드에서 결론 문장이 파형 **아래** 에 있음 → 위로 올릴 것

### 1-7. Block Diagram 단순 언급 (p.10)
- 단순 Topology · 구조 제시 : 적절함
- **But, Core IP 및 시스템 흐름 설명 : 표시 및 Labeling 필요**
- 박스만 그려 놓고 끝 ✗ → 핵심 블록 강조 · 신호 흐름 화살표 · 이름 라벨 ✓

### 1-8. Text 연결 및 Pointer Mismatch (p.11)
- 화살표 여러 개가 한 문장에서 뻗어 나와 교차 → 복잡성 ↑, 가독성 ↓
- Text 와 Pointer 가 Mismatch 면 **항목별 범례** 필요 (예 : 시 · 분 · 초 각각 색 구분)
- 내용과 Pointer 가 1:1 일치 → 가독성 · 가시성 ↑

### 1-9. 결론 및 고찰 (p.12)
- 단순 "검증 및 구현함" 텍스트 나열 → **What? How?** 누락
- **결론** : 설계 · 검증을 통한 **결과를 논하는 과정, 정상 동작 여부 및 수치 기입**
- **고찰** : **현 시점 Issue or 향후 Develop** 내용
- 결론 / 고찰 **분류 필요** (한 덩어리 문단 ✗)
- "Simulation 을 통해 FIFO 동작을 검증하였다." 한 줄 결론 → 아래 질문에 답이 있어야 함
  - 만약 못했다면? / 어떻게 검증? / 왜 그렇게 검증? / 동작 특성은?

### 1-10. 결론이 없는 슬라이드 (p.13)
- 결론이 없다 → 내용 전달 X (**특히 Sim. Result**)
- **Title 에 맞게 간략하게** 결론 기술 — 핵심 요약해 짧게
- 제목 바로 아래 결론 박스 1 줄 → 그 밑에 파형

### 1-11. 제목과 무관한 내용 구성 (p.14)
- 맥락 없는 내용 & **용어 오용** → 질문받을 가능성 多
- Slide 재구성 or **용어 뜻 알고 사용**
- 예 : "설계 **규약** 3 가지" (규약이 맞는 용어인가?), "왜 7 블록으로 묶었나" 에 대한 답이 "동작은 하나도 바뀌지 않았다" (질문에 대한 답이 아님)
- **적용** : 소제목 문장이 질문형이면 본문이 그 질문에 직접 답하는지 확인

### 1-12. Text Point 작은 경우 (p.15)
- 핵심 내용 Font Size ↓ → 가시성 · 가독성 ↓, **주석으로 오해**할 가능성 ↑
- **Font Size ↑ & 상단 배치** → 내용 전달 · 가시성 ↑
- 지적된 예 : 그림 아래 한 줄짜리 작은 글씨 설명 (실제로는 핵심 내용)

## 2. 레퍼런스 — 따라 할 것 (Ⅱ, p.17~28)

### 2-1. Pin Description 작성 (p.17)
- **장표(표)** 로 Pin I/O · Description 요약 — Datasheet 에서 많이 쓰는 방법
- 예 : `보드 입력 | PC 입력 | 시계 기능 | 스톱워치 기능 | 센서 기능` 열로 Btn_U/L/R/D, Sw[n], Led 를 행으로
- 보드 사진에 번호 Callout + 하단 Callout 번호 ↔ Component 표

### 2-2. Sim. Result 설명 표기 방식 1 (p.18)
- 각 Waveform 상태 설명 · Labeling → 내용의 개연성 ↑ (순차 · 논리 구조)
- 파형 위에 번호 `1) UART_RX/rx_done → FIFO_RX/push` … `5)` 를 박스로 표기, 하단에 같은 번호로 설명
- **해당 구간 확대 & Re-capture** → 가시성 ↑ (전체 파형 + 확대 inset, 연결선)
- 값 해석 박스 : `72 = 0111/0010` 처럼 버스 값 → 의미 변환을 크게

### 2-3. Sim. Result 설명 표기 방식 2 (p.19)
- 파형 위 해당 위치에 **값 라벨** 직접 표기 (`0x2f('/')`, `0x74('t')` …)
- 구간 화살표 + 설명 (`약 21 번의 baud tick 을 기다리는 동안 rx_done 발생 X`)
- 계산 근거 박스 (`1 baud tick 은 1/9600 = 104.160 us`)
- FSM 상태 시퀀스를 파형 위에 기입 (`IDLE → START → WAIT → COUNT → DISTANCE`) + 하단 1 줄 결론

### 2-4. Sim. Result 설명 표기 방식 3 (p.20)
- **Case 분류** (Case 1. /get. Operation, Case 2. /time. /range. …) → Target 검증 명확, 설명 용이
- 파형 위 큰 번호 `1.` `2.` `3.Discarded!` `4.` + 화살표, 상태 구간 라벨 (`IDLE / TIME / RANGE …`)
- **Figure 번호 + 캡션** (`Figure 20. Waveform result of /get. Operation`)
- Key Table (입력 → 기대 출력) 을 파형 옆에 배치

### 2-5. Block Diagram 표현 및 Core IP 표기 (p.21)
- Block Diagram : 필요한 IP Block + **Path 를 굵은 반투명 화살표로**, **범례** (`*Data path` 빨강 / `*Control path` 파랑)
- RTL Schematic : Core IP 를 **색 박스로 묶고 `*Ascii Decoder` 처럼 라벨**

### 2-6. Code & IP Block Matching (p.22)
- 왼쪽 : 순차적 설명 bullet / 가운데 : IP 블록 (포트) / 오른쪽 : 코드
- 설명 줄 ↔ 코드 줄을 **같은 색 Square Box + 화살표**로 연결
- 포트 신호 → 해당 코드 라인 연결 → 설명 용이 · 가시성 ↑

### 2-7. 구체적 수치 언급 (p.23)
- 수치 → 간단명료, 동작 특성을 **객관적으로** 표현
- 예 : 큰 숫자 카드 `9600 bps` · `8 data bits` · `1+1 start+stop` · `0 parity`, `10 ns (1 클럭)` · `≈1.04 ms (1 byte)` · `≈104,000 배`
- **단, 너무 많은 수치는 지양** → 본질을 흐림 (카드 3~4 개 수준)

### 2-8. Checklist & Expectation (p.24) ★ 시뮬 시나리오 표 기본형
- **Input Stimulus / OP Check** (입력 · 동작) → **Checklist** (확인 내용) → **Expectation** (예상 결과)
- 열 구성 : `순서 | 입력/동작 | 확인 내용 | 예상 결과`
- Checklist → 순차 확인으로 검증 신뢰성 ↑ / Expectation → 정상 여부 판단 용이 · 단계별 Debugging 유리
- 표 아래 1 줄 요약 (이 시나리오가 무엇을 검증하는지)

### 2-9. 검증을 위한 Modeling (p.25)
- Ideal 신호가 아닌 **Noise 신호 (@Input)** 로 검증 → 신뢰성 ↑ (예 : 버튼 채터링 모델)
- **Modeling 및 근거 명확** ("자극을 이렇게 설계한 이유" 박스) → 논리적 타당성 ↑, 실무 Insight ↑
- 검사 항목 표 (`# | 검사 항목 | 판정`) + 자극 조건 표 (`start=1,10ns | delay | echo=1, 580us`)

### 2-10. Table 의 적절한 활용 (p.26)
- 평가 항목 · Issue List-Up → 정리 유용, 단계적 분석 · 가시성 ↑
- 예 : "검증 전략 — 블록마다 전용 테스트벤치" (`TB | 대상 블록 | 축소 파라미터 | 검사 항목`), "해결한 이슈 12 건" (`# | 이슈 | 원인 | 조치`)
- 표 위에 **1 줄 요약 부제** (빨간 박스로 강조된 부분)
- **단, PPT 내 장표 비율 ↑ → 논점 흐림**. 적절히 사용

### 2-11. Timing Diagram 분석 (p.27)
- Timing Diagram → 시스템 분석, 단계적 동작 특성 설명 용이
- 구간별 빨간 박스 + 번호 라벨 (`① MCU Start` `② DHT 응답` `③ 40-bit Data`), 하단에 수치 (`START ≥ 18 ms`, `응답 Low 80 µs`)
- **단, 기재한 수치를 논리적으로 설명할 줄 알아야 함 (기준 및 시점)** — 발표 때 질문 대비

### 2-12. Abstract 및 Conclusion (p.28)
- **Abstract** → 핵심 요약, 간결 : 카드 3 개 `1 Project Overview` / `2 Project Goal` / `3 Conclusion`
  - Conclusion 카드에 수치 : `Worst Slack Time : 2.560 ns`, `Power : 110 mW`, `Utilization : LUT 4% / LUTRAM 1% / FF 2% / IO 35%`, `Demo : Success`
- **Conclusion** → 간결, **구체적 수치** (검증 신뢰도 ↑) : `POINT. 01 ~ 04` 카드형, 카드마다 소제목 + 1~2 줄

## 3. Trouble Shooting (Ⅲ, p.30~36)

### 3-1. 기본 논리 (p.30) — 반드시 4 단계
| 단계 | 이름 | 의미 | 필요한 자료 |
|---|---|---|---|
| ① | 현상 | 문제 인식 | 문제 파형 · 보드 사진 · 증상 수치 |
| ② | 원인 | 분석 | 원인 코드 · 타이밍 리포트 · 원인 파형 |
| ③ | 문제 해결 | A / I (Action Item) | 수정 코드 (Before / After), 적용 항목 |
| ④ | 적용 결과 | 비교 및 도출 | **Before & After 비교 Data** (파형 · 수치 · 사진) |

### 3-2. 보강 요청 사례 (지적된 누락)
- 사례 1 (p.31) — `구분 | 현상 | 개선 방향` 표만 있음 → 현상 자료 누락, **원인 ② 누락**, 수정 내용 자료 X, **적용 결과 ④ 누락**, 비교 Data 누락
- 사례 2 (p.32) — 보드 사진 Before/After 는 있음 → 원인 자료 누락, **해결 방안 ③ 누락**, **적용 결과 ④ 누락**, 비교 결과 자료 보완
- 사례 3 (p.33) — `As-Is → 디버깅 → To-Be` 텍스트 + PASS 표 → **단순 Text 서술 지양**, 현상 · 원인 · 해결 자료 누락, **적용 결과 ④ 누락**, 비교 결과 누락

### 3-3. 레퍼런스 (보완 코멘트 포함)
- 레퍼런스 1 (p.34) — 좌 `증상 ① / 원인 ②`, 우 `해결 ③ / 검증 ④` 2 칸 박스 + 번호 → 추가 요청 : 현상~해결 자료 보강, **Sim. 비교 결과 (Before & After)**, 적용 Item 자료, 기입한 수치 Data
- 레퍼런스 2 (p.35) — Negative Slack : ①② 원인 코드 (`/58`) + 실패 Timing Report → ③ 수정 코드 (`*1130 >> 16`) → ④ 통과 Timing Report (WNS 2.988 ns). 추가 요청 : **As is → To be 비교 Data**, `현상 : ~ , 원인 : ~` 순차 정리
- 레퍼런스 3 (p.36) — Done flag 누락 : 코드 Before/After + ILA 캡처 `Flag Missing → Flag Generated`, ComPort `No Return → Return!`

### 3-4. Trouble Shooting 슬라이드 양식 (권장)
```
[제목] Trouble Shooting N : <한 줄 문제명>
[상단 결론] 원인 : ~ / 조치 : ~ → 결과 : <수치>        ← 두괄식
[타임라인] ①현상 ─ ②원인 ─ ③해결 ─ ④적용 결과
[좌]  ① 현상 : 문제 파형/사진 + 1 줄    ② 원인 : 코드 박스 + 1 줄
[우]  ③ 해결 : 수정 코드 (변경 줄 박스) ④ 결과 : Before | After 파형/수치 나란히
[하단 작게] Note. 계산 근거
```
- 4 칸 모두 **자료(그림 · 코드 · 수치)** 필수. 텍스트만 있는 칸 ✗
- 분량 많으면 2 장 (①② / ③④) 허용 — 타임라인에서 현재 단계 강조

## 4. 슬라이드 유형별 양식 (이 프로젝트 적용)

### 4-1. 공통 레이아웃
```
┌──────────────────────────────────────────────┐
│ 섹션 번호 · 제목 (Title 과 내용 일치)              │
│ [결론 박스] 검증 결과 : ~ 정상 동작 (수치)          │ ← 두괄식, 큰 글씨
│ • 개조식 핵심 2~4 줄 (번호 = 그림 번호)              │
│ ┌──────────── 그림/파형/표 ──────────────┐     │
│ │  ① ② ③ 번호 박스 · 화살표 · 범례          │     │
│ └────────────────────────────────────┘     │
│ Figure N. 캡션        Note. 계산 근거 (작게)      │ ← 미괄식 영역
└──────────────────────────────────────────────┘
```
- 결론 · 핵심 bullet 은 본문보다 **큰 글씨**, Note 만 작게
- 강조색은 1~2 개 (예 : 빨강 = 핵심, 파랑 = 보조). 형광펜 남발 ✗
- 빈 영역이 1/3 이상이면 블록도 · 표 · 사진으로 보강, 단 여백은 유지

### 4-2. 권장 전체 목차 (레퍼런스 종합)
1. 표지 (프로젝트명 · 날짜 · 작성자)
2. Contents
3. **Abstract** — Overview / Goal / Conclusion(수치) 카드 3 개 (Ⅱ-12)
4. 프로젝트 개요 · 개발 환경 — 순서도 or 블록도 + 보드 사진으로 공백 제거 (Ⅰ-2)
5. **Pin Description / 입력 기능 표** — 버튼 · 스위치 · LED · FND (Ⅱ-1)
6. **Block Diagram** — Data / Control path 범례 + Core IP 라벨 (Ⅱ-5)
7. 모듈 설명 — FSM / Timing Diagram + Status Matching, Code ↔ Block Matching (Ⅰ-4, Ⅱ-6, Ⅱ-11)
8. **검증 전략** — 블록별 TB 표 (Ⅱ-10), Modeling 근거 (Ⅱ-9)
9. **시뮬레이션 시나리오 통합 표** — 순서 / 입력·동작 / 확인 내용 / 예상 결과 (Ⅱ-8)
10. 시뮬레이션 결과 — 시나리오 1 장씩, 결론 상단 + 번호 주석 파형 + Figure 캡션 (Ⅱ-2~4)
11. **Trouble Shooting** — ①~④ + Before/After (Ⅲ)
12. **결론 및 고찰** — 결론(정상 여부 + 수치) / 고찰(현 Issue · 향후 Develop) **분리** (Ⅰ-9, Ⅱ-12)
13. Q&A · Thank you

### 4-3. 시뮬레이션 결과 슬라이드 (가장 많이 지적됨)
- 제목 : `시나리오 N : <검증 대상>` — 제목과 파형 내용 일치
- 상단 결론 1 줄 : `검증 결과 : <동작> 정상 — <수치>` (필수, 생략 금지)
- bullet 번호 ① ② ③ = 파형 위 번호 박스 = wcfg 마커 번호 = 시나리오 표 순서 번호
- 파형 : 전체 캡처 + 필요 시 핵심 구간 확대 inset (Re-capture)
- 버스 값은 의미로 변환해 라벨 (예 : `sec = 8'h3B → 59`)
- 상태 시퀀스 라벨 (예 : `IDLE → EDIT_S → EDIT_M`)
- 하단 : `Figure N. ~` + `Note.` 계산 근거 (예 : `100 MHz × 1 s = 100,000,000 clk`)

### 4-4. 결론 및 고찰
- 결론 : 무엇을 / 어떻게 / 왜 그렇게 검증했고 / 결과(정상 여부 + 수치) — POINT 카드 3~4 개
- 고찰 : 현 시점 Issue, 향후 Develop — 결론과 **다른 박스**
- 가능하면 수치 : Worst Slack, Utilization (LUT/FF/IO %), Power, 시뮬 PASS 건수, Demo 결과

## 5. 표현 규칙 상세

| 항목 | 규칙 |
|---|---|
| 문장 종결 | `~함 / ~임 / ~확인 / ~전환 / ~발생` 또는 명사형. `~다.` 종결 금지 |
| 화살표 표기 | 인과 · 흐름은 `→`, 증감은 `↑ ↓` |
| 번호 | 원문자 `① ② ③` 또는 박스 번호. 텍스트 번호 = 그림 번호 1:1 |
| Highlight | 슬라이드당 1~2 곳. 결론 수치 · 핵심 신호명에만 |
| 포인터 | 한 문장 = 한 화살표. 여러 대상이면 범례 · 색 구분 (시 · 분 · 초) |
| 폰트 | 핵심 내용 크게 · 상단. 작은 글씨는 Note/주석 전용 |
| 수치 | 단위 필수 (ns, µs, ms, MHz, bps, %). 슬라이드당 핵심 3~4 개 |
| 표 | 표 위에 1 줄 요약 부제. 전체 PPT 에서 표 비율 과다 ✗ |
| 용어 | 뜻이 불명확한 용어 (규약, 방어형 등) 사용 금지. 신호명 · 모듈명은 코드와 동일 표기 |
| Figure | 파형 · 그림마다 `Figure N.` 캡션 |
| 블록도 | Core IP 라벨 + Data/Control path 범례 + 흐름 화살표 |

## 6. 최종 체크리스트 (PPT 생성 후 Claude 가 슬라이드마다 자체 점검)

- [ ] 모든 bullet 이 개조식 (`~다.` 로 끝나는 문장 없음)
- [ ] 결론/요약이 슬라이드 **상단** 에 있음 (특히 Sim. Result)
- [ ] 제목과 본문 내용이 일치, 같은 제목 슬라이드 중복 없음
- [ ] 텍스트 항목 ↔ 그림 위치가 번호 · 박스 · 화살표로 1:1 연결
- [ ] 화살표 교차 · 다대일 포인터 없음 (있으면 범례)
- [ ] 긴 서술은 표 · 그림으로 대체, Highlight 1~2 곳
- [ ] 빈 공간 과다 없음 / 꽉 채우지도 않음
- [ ] 핵심 글씨가 작지 않음 (주석으로 오해 X)
- [ ] 정상 동작 근거가 **수치** 로 제시됨 (단위 포함, 과다 X)
- [ ] 블록도에 Core IP 라벨 · 범례
- [ ] 파형마다 Figure 캡션, 필요 시 확대 inset
- [ ] 결론 / 고찰 분리, 결론에 What · How · Why · 수치
- [ ] Trouble Shooting 은 ①현상 ②원인 ③해결 ④적용 결과 + Before/After 비교 Data 모두 있음
- [ ] 슬라이드에 적은 수치를 발표자가 기준 · 시점으로 설명 가능 (근거를 Note 에 남김)
