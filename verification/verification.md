## 1. 공통 환경

### 1.1 시뮬레이터 (A가 실측함, 100 MHz 실시간 기준)

| 도구 | 버전 | 속도 (sim 1 ms 당 wall) | 쓰는 곳 |
|---|---|---|---|
| Verilator `--binary --timing` | 5.032 | **≈ 24 ms** (sim 1 s ≈ 24 s) | **기본 회귀**. 로그만, 파형 없음 (Verilator 는 `$dumpoff` 를 무시해서 파형이 폭증함) |
| Icarus `-g2012` | 12.0 | ≈ 450 ms (sim 1 s ≈ 7.5 분) | **파형 추출용**. FAIL/DEFECT 가 찍힌 Phase 하나만 `+phase=N +wave=...` 로 재실행 |

- 두 도구 모두 확인됨: 계층 참조 쓰기(프리로드), `$timeformat`, `$value$plusargs`, `wait`, `@(posedge ...)`.
- TB 는 두 도구에서 같이 돌아야 한다 → **SV 기본 문법만**(class·interface·assertion property 금지, `string`·`logic`·`task`·`function` 은 OK).
- **2.1 s 넘는 지연은 `integer` 오버플로**(2^31 ns) → 지연값은 `time` 또는 `longint` 변수/`64'd` 상수로 쓴다.
- Verilator 는 2-state 라 X 를 못 본다 → 리셋 직후 X 검사는 Icarus 로 한 번(§5 TOP-1 Phase 0).

### 1.2 버튼 · 스위치 자극 기준 (실측 근거)

디바운서 = 4 kHz(250 µs) 샘플 8칸 AND → **8 샘플 연속 1** 이어야 눌림.
A가 실측한 경계 (Icarus, 실제 클럭):

| 누름 길이 | 결과 | 비고 |
|---|---|---|
| < 1.75 ms | 항상 무시 | 7 샘플 이하 |
| 1.75 ~ 2.0 ms | **위상에 따라 0 또는 1** (회색 구간) | 샘플 시점과의 위상 |
| ≥ 2.0 ms | 항상 1 펄스 | |
| 누른 상태 중간 0 글리치 200 µs / 300 µs | **2 펄스 (두 번 눌림)** | 디바운서 한계 (§5 TOP-1) |
| 뗀 뒤 다시 누르기까지 간격 260 µs | 2 펄스 | 재입력 최소 간격 ≈ 250 µs |

- 표준 `press()` = **누름 5 ms + 뗌 5 ms** (사람 손 100 ms 보다 짧지만 2 ms 이상이라 RTL 동작은 같다. 시뮬 시간 절약 목적이고 클럭은 그대로).
- 스위치 변경 뒤 최소 1 µs 기다린 뒤 검사 (조합 경로 정착).
- 버튼 하나 = 디바운서 출력 `dut.w_btnX` 에 **정확히 1클럭(10 ns) 펄스**. 모든 TB 에 펄스 카운터 모니터를 둔다(§1.4).

### 1.3 프리로드(backdoor) 규칙 — "주파수를 줄이지 않고" 시간을 건너뛰는 방법

- **허용**: datapath 카운터 레지스터 값만 `@(negedge clk)` 에서 직접 대입.
  - 시계: `dut.U_WATCH_DATAPATH.U_{HOUR,MIN,SEC,MSEC}_COUNTER.counter_reg`
  - 스톱워치: `dut.U_STOPWATCH_DATAPATH.U_{HOUR,MIN,SEC,MSEC}_COUNTER.counter_reg`
  - 타이머: `dut.U_TIMER_DATAPATH.{min_reg,sec_reg,msec_reg}`
- **금지**: tick 생성기(`U_TICK_GEN_100HZ`, `U_CLK_GEN_4KHz`) 카운터, FSM 상태, clk 건드리기.
- 대입 직전에 `@(posedge dut.w_tick_10ms); @(negedge clk);` 로 tick 직후에 맞춘다 → 다음 tick 이 정확히 10 ms 뒤라서 기대 시각이 결정적이다.
- 프리로드할 때마다 `[INFO][PRELOAD] <경로> = <값>` 로그 필수 (발표 때 "백도어로 시간 점프" 라고 설명 가능하게).
- **정확도 검사(1 s = 1e8 clk, 타이머 10 s)는 프리로드 없이** 실제로 흘려서 잰다.

## 2. WATCH (ahnsung) — 시계

**컨셉**: 리셋 = 12:00:00.00(오후 12시, 12시간 표시). sw2=1 이면 설정, 자리 단위(분 일 · 분 십 · 시) 커서, U/D 로 그 자리만 ±(올림 없음). 초·1/100초는 설정 불가. 설정 중에도 시계는 흐른다. sw3 로 12/24 표시.

### 2.1 경계조건 + 이유

| ID | 경계조건 | 왜 (논리적 이유) |
|---|---|---|
| WB1 | 23:59:59.99 → 00:00:00.00 | 4단 carry 가 **한 tick 에 동시에** 넘어가는 유일한 순간. 한 단이라도 carry 타이밍(1클럭 지연 o_tick)이 어긋나면 여기서만 틀린다 |
| WB2 | 분 59→00 (시 +1), 초 59→00 (분 +1) | carry 경로마다 TIMES-1 비교가 맞는지. off-by-one 이 가장 흔한 곳 |
| WB3 | 설정 wrap: 분 59 +1 → 00 · 00 -1 → 59 / 분십 55 +10 → 05 · 05 -10 → 55 / 시 23 +1 → 0 · 0 -1 → 23, **이때 윗자리 안 바뀜** | 설정은 "그 칸만 돈다"가 사양. 흐름용 carry 와 설정용 wrap 이 같은 카운터에 있어서 섞이기 쉽다 |
| WB4 | 12/24 변환: 0시 → "12"(오전), 11 → 11(오전), **12 → "12"(오후)**, 13 → "1"(오후), 23 → "11"(오후) | 12시간제는 0과 12가 둘 다 "12"로 보이는 비선형 매핑. `>` / `>=` 하나로 틀어진다 |
| WB5 | 설정 중 흐름 carry: 설정 모드에서 23:59 로 맞춘 뒤 초가 59→00 넘어가면 00:00 이 됨 | 설정 중에도 시계가 흐르는 설계 → "맞췄는데 바뀌었다"는 사용자 혼란 지점. 현행 동작을 기록 (INFO) |
| WB6 | tick 과 U 펄스가 같은 클럭 → tick 우선, 버튼 1회 손실 | 설계 주석의 의도된 우선순위. 손실 1회가 허용 범위임을 근거로 남김 |
| WB7 | 1 s = 정확히 100,000,000 clk | 100 Hz tick = 1,000,000 clk 주기. 실시간 시계의 정확도 기준 |

| ID | 체크 | 이유 |
|---|---|---|
| WC1 | 리셋 직후 12:00:00.00, cursor=3, set_mode=0, LED=8009 | 보드 켜자마자 보이는 첫 화면. 데모 1번 |

## 3. STOPWATCH (jonghyuk) — 스톱워치

**컨셉** (`f39f97e` 기준): R = RUN/STOP 토글, **L = 클리어(STOP 에서만**, 랩도 해제), **U = 카운트 방향 토글(STOP 에서만)**, D = 랩(RUN/STOP 모두, 누르면 그 순간 고정 표시, 다시 누르면 실시간). RUN 중 L·U 는 무시. 00:00:00.00 ~ 23:59:59.99 순환. 화면 밖에서도 계속 돈다.

### 3.1 경계조건 + 이유

| ID | 경계조건 | 왜 |
|---|---|---|
| SB1 | 업: xx:xx:59.99 → +1분, 59:59.99 → +1시, **23:59:59.99 → 00:00:00.00** | 시(TIMES=24) wrap 은 시계와 같은 구조지만 스톱워치 전용 `stopwatch_tick_counter` 라 따로 검증해야 한다 |
| SB2 | 다운: **00:00:00.00 → 23:59:59.99** (전 자리 borrow 동시) | 다운 카운트는 `counter==0 → TIMES-1` 이라 업과 비교 조건이 다르다. 0 에서의 borrow 체인은 업 carry 와 대칭이 아니라서 별도 확인 |
| SB3 | 측정 오차: RUN 시작 후 첫 증가까지 0~10 ms | tick 이 공용(항상 흐름)이라 시작 시점이 tick 위상과 무관 → 측정값은 **최대 1 count(10 ms) 오차**. 이게 사양 한계임을 근거로 남김 |
| SB4 | 랩: 누른 순간 값 고정, 내부 카운터는 계속 증가, 해제 시 실시간 값으로 복귀 | 표시와 내부 값이 분리되는 유일한 기능 |
| SB5 | **RUN 중 L → 무시** (값 유지, RUN 유지, 랩 상태도 유지) | v4 초판에서 보드로 발견된 버그(RUN 중 L 이 잰 시간을 지움)의 수정 확인. 회귀 방지 핵심 항목 |
| SB6 | **RUN 중 U → 무시** (방향 유지) / STOP 에서 U → 방향 바뀜, 다음 RUN 부터 반영 | 위와 같은 수정. `mode_reg` 토글 조건에 `c_state == STOP` 이 붙음 |
| SB7 | STOP 에서 **R 과 L 이 같은 클럭** → RUN 이 되면서 0 으로 지워짐 | README 에 적힌 남은 차이(판서 FSM 은 R 우선·안 지움). 두 버튼을 **같은 시각에 누르면** 디바운서 4개가 같은 4 kHz 샘플을 쓰므로 실제로 같은 클럭 펄스가 된다 → 재현 가능. `[LIMIT]` 로 기록 |

### 3.2 체크리스트 + 이유

| ID | 체크 | 이유 |
|---|---|---|
| SC1 | 리셋 → 0, STOP | 초기 상태 |
| SC2 | R 한 번 RUN, 또 한 번 STOP, STOP 동안 값 유지(200 ms 관찰) | 기본 동작 |

## 7. 결함 주입 (현업 환경 결함 — 설계 로직은 건드리지 않는다)

### 7.0 선정 원칙 (v3 에서 바뀜)
- **코드 작성 실수(엣지 검출 누락 · off-by-one · carry 누락 등)는 결함 케이스에서 뺀다.** 그건 작성자 실수이고 현업 환경에서 생기는 문제가 아니다 → 기능 TB(§2~4)의 경계 검사가 잡을 몫.
- 결함 = **설계는 그대로인데 보드/환경 조건이 바뀌는 상황**: 클럭 위상(스큐) · 스위치 노이즈 · 사람의 입력 시점 · 전기적 글리치.
- 주입 방법 = **결함 주입기(fault injector)** 를 Top 의 핀 ↔ 설계 사이에 끼운다. 주입기는 **sw15**(핀 `R2`, 지금 안 쓰는 스위치)로 켜고 끈다 → **같은 비트스트림에서 sw15 = 0 이면 정상, 1 이면 결함 상황** (보드 시연에서 바로 비교 가능).
- 설계 모듈(카운터 · FSM · 디바운서 · FND) 파일은 **한 글자도 안 바꾼다**. 바뀌는 건 Top 의 연결 몇 줄 + 주입기 파일 + xdc 1줄.
- 원본 요청의 예시 3개(클럭 위상 · 스위치 노이즈 · 버튼 입력 시간) + 전기적 글리치 1개 = **4 종**. 발표 시간에 맞춘 수.

#### F1 — FND 자리선택(com)과 숫자(data)의 위상 차이 → 고스팅
- **현업 상황**: 다이나믹 구동 FND 에서 애노드 구동 트랜지스터의 turn-off 지연 · 배선 길이 차이 · 다른 위상의 스캔 클럭 때문에 **com 이 data 보다 늦게 바뀜**. 바뀌는 순간 이전 자리에 다음 자리 숫자가 잠깐 켜져서 **잔상(고스팅)**. 이 설계는 자리 사이에 블랭킹 구간이 없어서(빈칸 슬롯은 4자리 다 돈 뒤에만 있음) 위상 차이에 그대로 노출된다.
- **주입기** `fault_com_skew.v`: `fnd_com` 출력 경로에 "늦게 바뀌는" 지연 모델. com 입력이 바뀌면 N 클럭 동안 이전 com 을 유지한 뒤 바꿈 (4비트 레지스터 + 카운터, 시프트 레지스터 아님). `parameter N`, sw15=0 이면 N 무시하고 그대로 통과.
- **주입 위치**: `stopwatch_watch.v:258-275` FND_CON 의 `.o_fnd_com(fnd_com)` → 내부 wire `w_fnd_com_raw` → 주입기 → `fnd_com`.
- **보드**: sw15 = 1 (N = 12,500 = 125 µs = 슬롯의 1/2, 눈에 보이게 과장) → 각 자리에 옆 자리 숫자가 겹쳐 보임.
- **TB** `tb_f1_com_skew`: 화면 12:34(프리로드, 자리값이 모두 달라야 고스트가 보임). N = 0 / 500(5 µs) / 3,000(30 µs) / 12,500(125 µs) 각각 20 ms 실행 → fnd_monitor(§5.2)가 슬롯마다 "틀린 숫자가 켜진 시간"을 측정 → `[DEFECT][F1] AN0 shows '3'(AN1 digit) for 30.000 us per slot (12.0 % duty)` 형식 + N 별 표. N=0 은 PASS 여야 함.
- **트러블슈팅 포인트**: 자리 전환 때 1 슬롯 일부를 블랭킹(모든 com off)으로 두면 해결.

#### F2 — 스위치 채터링 / 노이즈
- **현업 상황**: (a) 버튼을 누르지 않았는데 EMI 로 버튼 선에 짧은 1 스파이크, (b) 낡거나 살짝 누른 스위치가 **누르고 있는 동안 잠깐 끊김(0 dropout)**.
- **이 설계의 비대칭**: 디바운서는 "8 샘플 연속 1 → 눌림"이지만 **떼는 쪽은 0 샘플 하나로 즉시 해제** (§1.2 실측: 누른 중 200 µs 이상 끊기면 2 번 입력). 그래서 (a) 는 견디고 (b) 에는 약하다 — 발표 포인트.
- **주입기** `fault_chatter.v` (버튼 4개 앞에 각각): sw15=1 일 때
  - 안 누름: 결정적 스파이크 열 (1 µs · 50 µs · 500 µs · 1.5 ms 폭, 간격 7 ms) OR
  - 누르는 중: 20 ms 마다 300 µs 동안 0 으로 끊음 (AND)
- **주입 위치**: `stopwatch_watch.v:91-117` 디바운서 `.i_btn(btnX)` → `.i_btn(w_btnX_inj)`.
- **보드**: sw15 = 1 → 시계 설정에서 U 를 **꾹 누르면 분이 저절로 연타**(약 22 ms 마다 +1), 타이머 U 한 번 누름에 +10초가 여러 번. 안 누를 때는 아무 일 없음.
- **TB** `tb_f2_chatter` (TB 자극으로 같은 파형을 버튼 핀에 직접 넣어도 됨 — 주입기 RTL 과 TB 자극 둘 다 확인):
  - P1 스파이크 노이즈 200 ms (안 누름) → 펄스 0 → `[PASS]` (견고함)
  - P2 바운스 패턴(§5.1) → 펄스 1 → `[PASS]`
  - P3 누름 100 ms + 끊김 300 µs × 4 회 → 펄스 5 → `[DEFECT][F2] btnU extra pulse #k at <t>` (각 추가 입력 시각), 시계 분 +5 / 타이머 +50초
  - P4 끊김 폭 sweep 50 · 100 · 200 · 250 · 300 µs × 위상 4 개 → 2번 입력이 되는 경계 표 (250 µs 이상이면 항상)
- **트러블슈팅 포인트**: 해제도 "8 샘플 연속 0" 을 요구(히스테리시스)하면 해결.

#### F3 — 버튼 입력 시점 오차 (RTL 변경 없음, 자극만)
- **현업 상황**: 사람이 누르는 순간은 내부 10 ms tick 과 위상이 무관하다. 100 Hz tick 이 Top 에 하나(공용, 항상 흐름)라서 RUN 시작 시점이 tick 사이 어디든 될 수 있다 → **같은 1.000 s 를 재도 99 또는 100 count**, 타이머는 **최대 10 ms 짧게** 끝남 (README 에 적힌 구조상 대가). 또 2 ms 근처의 "톡" 치는 짧은 입력은 위상에 따라 씹힌다.
- **주입기 없음** — 폴더에는 원본 src 그대로 + TB 만. 보드에서는 재현이 아니라 시뮬 근거로 설명.
- **TB** `tb_f3_press_timing`:
  - P1 스톱워치: RUN 시작 위상을 tick 기준 0, 1, …, 9 ms 로 10 번, 매번 RUN 구간(`w_run_stop`) = 정확히 1.000 s → count 표 (99/100 분포). `[LIMIT][F3] phase=3ms count=99 (err -10ms)`
  - P2 타이머: 프리로드 00:01.00, 시작 위상 0~9 ms 10 번 → `posedge w_tm_run` → `posedge w_tm_alarm` 간격 표, 전부 (0.99 s, 1.00 s] 이어야 함 (벗어나면 FAIL)
  - P3 짧은 탭: 누름 1.5 · 1.8 · 1.9 · 2.0 ms × 위상 4 개 → 인식/무시 표 (§1.2 회색 구간 재현)
- **트러블슈팅 포인트**: RUN 시작 때 tick 카운터를 0 으로 맞추면(v2 의 개별 tick 방식) 오차가 사라지지만 자원 · 공용성과 맞바꿈.
- 시뮬: ≈ 25 s sim → Verilator ≈ 10 분 (가장 김, P0 마지막에).

#### F4 — 리셋 라인 글리치 (EMI)
- **현업 상황**: btnC(rst)는 **비동기 리셋**이고 필터 · 동기화가 없다. 모터 · 정전기 · 긴 배선에서 생기는 수 ns 글리치에도 전체 초기화. A 실측: 0.8 ns 짜리 클럭 비정렬 글리치 하나로 시계 09:41 → 12:00.
- **주입기** `fault_rst_glitch.v`: sw15 의 상승 엣지(2FF 동기화)에서 내부 rst 에 **1 클럭(10 ns) 펄스**를 OR. 사람이 btnC 를 누른 것과 구분하려고 LED 는 건드리지 않음.
- **주입 위치**: `stopwatch_watch.v` 의 모든 `.rst(rst)` / `.reset(rst)` / `.i_reset(rst)` → `w_rst_inj` (Top 에서만, 하위 모듈 무변경).
- **보드**: 시계 설정해 둔 시각 · 스톱워치 잰 시간 · 진행 중인 타이머가 sw15 한 번에 전부 사라짐 (타이머는 알람이 영원히 안 울림).
- **TB** `tb_f4_reset_glitch` (주입기 없이 TB 가 rst 핀에 직접 글리치):
  - 상태 준비: 시계 09:41(프리로드) · 스톱워치 RUN 0.30 s · 타이머 RUN 00:50
  - 글리치 폭 0.5 · 1 · 5 · 10 ns, 클럭 엣지와 비정렬 → 매번 감시자가 "rst 가 의도된 리셋 시퀀스(do_reset) 밖에서 1 이 됨" + "카운터가 갑자기 리셋값" 을 잡아 `[DEFECT][F4] unexpected reset glitch width=1.0ns at <t>: watch 09:41->12:00, sw 0.30->0.00, timer 00:50->00:00 (alarm lost)`
  - 다시 준비 → 다음 폭. 4 번 모두 DEFECT 가 기대값 (= 폭과 무관하게 전부 초기화된다는 것이 결론)
- **트러블슈팅 포인트**: 리셋 동기화기(비동기 assert · 동기 release) + 최소 폭 필터.

## 8. 콘솔 로그 규칙

- 시뮬 0 시각에 `$timeformat(-3, 6, " ms", 14);` → 모든 시각은 **ms, 소수 6자리(= ns 단위)**.
- 한 줄 형식: `[<%t>] [<LEVEL>] [<TB-ID>.P<phase>.<check-id>] <설명> | exp=<기대> got=<실제> | disp="<FND 문자열>"`
  - 예: `[  1203.450010 ms] [FAIL ] [WT2.P4.WB1] midnight carry | exp=00:00:00.00 got=00:00:59.00 | disp="00.00"`
- LEVEL:
  | LEVEL | 의미 |
  |---|---|
  | `PHASE` | Phase 시작/끝 (시작 시각 · 끝 시각 · 그 Phase 의 FAIL 수) |
  | `PASS ` | 검사 통과 (Phase 당 요약 1줄이면 충분, 개별 PASS 남발 금지) |
  | `FAIL ` | 기대와 다름 — **같은 검사 ID 는 처음 5번만 출력**, 이후 개수만 셈 |
  | `DEFECT` | 결함 TB 에서 결함이 처음 잡힘 (= 파형 바로가기 시각). 바로 다음 줄에 `wave window: <t-1ms> ~ <t+1ms>` |
  | `LIMIT` | 설계 한계(사양상 FAIL 아님) — 바운스 글리치, tick 우선 버튼 손실 등 |
  | `INFO ` | 프리로드, 현행 동작 기록(SB5, WB5) |
- 마지막 줄: `[<%t>] [SUMMARY] <TB-ID> src=<원본|defect_N> checks=<n> fail=<n> defect=<n> => PASS|FAIL|DETECTED`
- 타임아웃 watchdog: 각 TB 는 예상 시뮬 시간 × 2 에서 `[FAIL ] TIMEOUT` 후 `$finish`.
- 검색: `grep -E "FAIL|DEFECT|TIMEOUT" results/**/sim.log` 한 번으로 전체 이상 시각을 뽑을 수 있어야 한다.

```

│   ├── common/  tb_common.svh  fnd_monitor.sv

│   ├── top/        tb_top_1_btn_debounce.sv  tb_top_2_fnd_scan.sv
│   ├── run.sh        # ./tb/run.sh <tb_name|tb경로> [--sim verilator|icarus] [--src <dir>] [--phase N] [--wave]
│   └── run_all.sh    # P0 → P1 순서로 전부, 끝에 results/summary.md 생성
├── defect_1_fnd_com_skew/ … defect_4_reset_glitch/   (B, §7.2)
└── results/                                            (B)
    ├── <tb_name>/sim.log  [wave.vcd]                    # wave 는 Icarus --wave 재실행 때만
    ├── defect_N/orig.log  fault_off.log  fault_on.log  [wave.vcd]
    └── summary.md   # | TB | src | 결과 | fail 수 | 첫 이상 시각 | 파형 창 | 비고 |
```

- `run.sh` 기본값: `--sim verilator`, `--src ../boyun/merged_v4/src`, 모든 Phase, 파형 없음. 항상 `verification/` 에서 실행.
  - Verilator: `verilator --binary --timing -j 0 -Wno-fatal -Wno-lint -Wno-style --top-module <tb> -Itb/common <tb.sv> tb/common/fnd_monitor.sv <src>/*.v <src>/*.sv --Mdir results/<tb>/obj -o sim`
  - Icarus: `iverilog -g2012 -Itb/common -o results/<tb>/sim.vvp ... && vvp -n results/<tb>/sim.vvp +phase=N +wave=results/<tb>/wave.vcd`
- 파형 규칙: `+wave=` 가 있을 때만 `$dumpfile/$dumpvars(0, <tb>)`, 그리고 긴 대기 구간은 `$dumpoff`, 검사 전후 ±2 ms 만 `$dumpon` (Icarus 만 지원 — 그래서 파형은 Icarus 전용).
- 파형 보기: GTKWave(Windows 설치) 로 `wave.vcd`. 발표 캡처가 Vivado 여야 하면 같은 TB 를 xsim 에서 해당 Phase 만 실행 (TB 가 SV 기본 문법이라 그대로 됨).

## 10. 역할 분담 · 보고 방식

- **B**: TB/결함 폴더/스크립트 작성 → 컴파일 확인(`run.sh --build-only`: Verilator 빌드 또는 `iverilog` 컴파일만) → `B_to_A.md` 에 `RESULT`(type) 로 "실행 준비 완료: <TB 목록>, 실행 명령" 보고. **시뮬 실행은 하지 않는다.**
- **사용자**: `./tb/run.sh <tb>` 또는 `./tb/run_all.sh` 로 실행 → `results/` 에 로그가 쌓임.
- **A**: 사용자가 실행한 `results/**/sim.log` 를 읽고 FAIL/DEFECT 를 판정 → TB 기대값 문제면 B 에게 수정 요청, 설계 문제면 사용자에게 보고.

- (사용자 실행 후) 로그 판정은 A 가 한다. B 는 A 의 수정 요청을 받으면 TB 를 고치고 다시 컴파일 확인까지만.
- 원본 설계에서 FAIL 이 나오면 **설계 버그 후보** → 직접 고치지 말고(설계는 읽기 전용) `RESULT` 에 시각 + 로그 5줄 첨부. A 가 TB 기대값 문제인지 설계 문제인지 판정한다.
- 계획대로 안 되는 것(시간 초과, 계층 경로 없음, 도구 미지원)은 `BLOCKER`.
